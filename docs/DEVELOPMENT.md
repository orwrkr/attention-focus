# Development and Deployment

## Requirements

- Windows x64 and `rustup`, which installs the toolchain pinned in `rust-toolchain.toml`.
- MSVC C++ build tools and Windows SDK for native linking and bundled SQLite.
- Access to crates.io for the first dependency download.
- Python 3.11+ and pinned PDF dependencies for production packaging. Run
  `./scripts/setup-docs.ps1` once (creates target/docs-venv), or set
  ATTENTION_FOCUS_PYTHON to a Python with scripts/requirements-docs.txt installed.

The application uses eframe 0.37.0, tray-icon 0.26.1, rusqlite 0.41.0, Jiff 0.2.38,
and winresource 0.1.34. Cargo.lock records the resolved dependency graph.
Build from the repository root so .cargo/config.toml enables the static C runtime.
Icons are generated by build.rs and embedded in the Windows executable resources.

## Commands

```powershell
cargo fetch --locked --target x86_64-pc-windows-msvc
cargo fmt --check
cargo test --locked
cargo clippy --locked --all-targets -- -D warnings
./scripts/test-release-output.ps1
python ./scripts/test_release_tools.py
./scripts/setup-docs.ps1
./scripts/build.ps1
./scripts/verify-release.ps1
./scripts/export-user-guide.ps1
./scripts/package-production.ps1
./scripts/dev.ps1 -BuildOnly
./scripts/dev.ps1
```

The only distributed executable is `dist/AttentionFocus/attention-focus.exe`. The main
build also creates `target/debug/attention-focus.exe` for testing, the guide PDF, and the
release folder `dist/AttentionFocus-VERSION/`. That folder contains exactly the EXE,
User-Guide-VERSION.pdf and release.json, the three files a GitHub release attaches. Only the
EXE is needed to run, and it holds the license notices (ADR-0036). No databases, settings,
logs, PDBs, or build tools are shipped.
The final PE import audit found only Windows system
libraries and no separately shipped runtime or SQLite DLL (see T-0006).
The build script consumes Cargo's main release artifact and publishes it atomically.
Other files under target are internal build/test artifacts, not releases. A locked
current or obsolete EXE fails before compilation; a publication race also returns an
error. No alternate EXE, fallback directory, or automatic process termination is allowed.
If an agent launched a blocking app, it must offer to exit it and wait for approval.
Build output is ignored by Git. No installer or updater is added.
Runtime requirements on a clean Windows machine have not yet been verified; do not
describe this build as universally portable.

Cargo.toml is the version authority. FileVersion is major.minor.patch.0; ProductVersion
is the package version (with -dev for debug). The header, PDF, manifest, and release folder
identify the version. After releasing a version, changed production source/guide/build
inputs require a version bump and scripts/build.ps1. A build stamp ties the EXE to its
inputs; packaging refuses a stale EXE or a renamed version around old binaries.
scripts/build.ps1 automatically refreshes/verifies the folder after publishing outputs.
scripts/export-user-guide.ps1 also refreshes it; package-production.ps1 explicitly
rebuilds it from current prepared outputs. verify-release.ps1 verifies hashes, the file
allowlist, source fingerprint, both EXEs' metadata, and every embedded neutral icon size. Older
folders and ZIPs are release history. There is still one canonical loose production EXE.
Development-only scripts/dev.ps1 builds do not touch production or require its closure.

The guide source is docs/user-guide.md, exported by scripts/export_user_guide.py using
ReportLab and actual generated icon artwork. Review every PDF page after guide/layout
changes.

`third-party/THIRD-PARTY-NOTICES.txt` includes resolved Windows runtime crates, embedded font
attributions, and Rust standard-library notices. The EXE embeds it and shows it under About.
scripts/build.ps1 regenerates it before compiling, and CI fails when it is out of date. After
changing dependencies or the toolchain, run `python scripts/release_tools.py update-notices`
and commit the result. See third-party/README.md for provenance.

## Runtime files and data

No asset files are required beside the EXE. Fonts, window/tray icons, shell icon,
and version metadata are embedded. SQLite and the MSVC runtime are statically linked
by the Windows target configuration. The PDB is optional debugging information.
Windows system libraries and a working graphics driver are still required. No Rust,
Node, WebView2, or .NET runtime installation is needed for this native build.

The Windows LocalAppData known folder supplies fixed, independent profile directories:

- `%LOCALAPPDATA%/AttentionFocus/Production/`: packaged release data.
- `%LOCALAPPDATA%/AttentionFocus/Development/`: debug/development data.
- Each contains `window.ron` (geometry and interface preferences) and `focus.sqlite3`
  (history, checkpoints, activity, projects and tasks).
- Schema upgrades create `focus-before-vN-*.sqlite3` backups using SQLite, where N is the
  first version being upgraded to.
- SQLite creates any journals in the same profile directory.

Legacy files directly under AttentionFocus, and `source.sqlite3` files left in a profile by
older versions, are retained unchanged and unread. Development tests never create records
in Production.

Debug/cargo run defaults to Development; explicit `--profile production` is rejected
by debug builds. The packaged release defaults to Production. A release may explicitly
run `--profile development` for an optimized development session. Fixed data paths cannot
be overridden. Mutexes/window identities are per profile; each permits one instance.
A repeated manual launch asks that instance to show its window, then exits.
Development has a distinct title, visible profile label, app ID, and tray menu/tooltip.

Development builds stay under target/debug and do not replace the production EXE.
Use scripts/dev.ps1 while Production is running. Updating the production EXE still
requires exiting Production; locked-file rules apply. Exit a running Development
instance before rebuilding its executable. Never create fallback release copies.

Moving the EXE does not reset history. Back up the data directory after exiting. Startup
checks for linked entries in app storage before any persistent initialization. Nothing is
stored beside the EXE. Concurrent hostile link replacement is outside the threat model.

Application behavior is described in the [user guide](user-guide.md), and its design in
[ARCHITECTURE.md](ARCHITECTURE.md).

## Manual verification checklist

Automated tests do not exercise real desktop behavior. Check these in Development, using
disposable synthetic projects:

1. Move/resize the window, wait three seconds, hide it, and exit through the tray.
2. Relaunch; verify geometry restoration, including maximized/multi-monitor cases.
3. Check the EXE, taskbar, Alt-Tab, Task Manager, and both tray state icons.
4. Double-click the tray to start, then stop. Verify one change per double click and
   no unwanted window opening on surrounding single-click events.
5. Single-click the tray with the window hidden, minimized and behind another application.
   Launch the EXE again while it runs. Both must bring the window to the front.
6. Use Show Focus and Exit both visible and hidden; restart and check saved totals.
7. Verify interrupted recovery using disposable test history, never real history.
8. Check tray failure, unwritable storage, and a clean Windows machine.
9. Add several projects, rename while tracking, archive and restore, finish a task, and
   delete a never-tracked project. Check Unicode rendering.
10. Check report periods, custom dates, invalid timezone/date errors, daily/project/task
    totals, details, and separation of running/review time. Leave tracking across midnight
    and check the two sessions and the current-day period.
11. Check the three chart views in both themes, with one day, a week and a period over 92 days.
    Hover over marks, narrow the window, and track across a report refresh.
12. Switch Theme through all three choices and check the title bar. With Same as Windows, change
    the Windows app mode. Check scroll bars in the body, By day, Sessions, a long Timeline, and
    the project and time zone lists: each lies beside its content and never covers it.
13. Switch Language through Russian, German, Chinese, Japanese, Korean and Arabic, and back to Same
    as Windows. Check the header and report rows at the minimum width, the tray menu and tooltip,
    and that Arabic reads from right to left, including a date and a wrapped sentence.

Always use scripts/build.ps1 and the canonical dist/AttentionFocus/attention-focus.exe path.

## Releases on GitHub

`.github/workflows/release.yml` runs the same `scripts/build.ps1` on a hosted Windows runner. A
tag `vVERSION` matching `Cargo.toml` leads to a draft release for the owner to publish. A manual
run builds the same files and keeps them as a workflow artifact.

Signing stays off until the repository has the secret `SIGNPATH_API_TOKEN` and the variables
`SIGNPATH_ORGANIZATION_ID`, `SIGNPATH_PROJECT_SLUG` and `SIGNPATH_SIGNING_POLICY_SLUG`. Then the
workflow submits the unsigned EXE and waits up to an hour for a person to approve it in SignPath.
With the `release-signing` policy, `scripts/use-signed-exe.ps1` installs the signed copy and
rebuilds the release folder. With any other policy, such as `test-signing`, the EXE stays unsigned.
See [ADR-0033](decisions/0033-release-workflow-and-signing.md) and T-0037.
